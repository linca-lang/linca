# ADR-0006. `cases.json` is replaced by `//~` annotations as the only expectations

- **Proposed:** 2026-11-22, by TeseySTD
- **Affects:** compiler
- **Spec:** Compiler RFC §11
- **Cases:** tests/data/lang/cases.json, tests/data/lang/README.md
- **Status:** accepted

## Context

`tests/data/lang/cases.json` lists every case with `id`, `kind` (valid, invalid, pending), `section`, `root`
(file or directory) and `expect` (code, file, line). All of it is already in the case files: the id is the path,
the section is in the header line, `root` is `bad.linca` versus `bad/`, `kind` follows from the directory
and the file name, and `expect` is the set of `//~ CODE` annotations, which README names as the source of
truth. The index is written by hand and has already drifted: the cases added for ADR-0001, ADR-0002 and
ADR-0003 (`E0221_type_base_collection`, `E0221_type_base_nullable`, `E0102_newline_in_string`,
`valid/07_attributes/keyword_parameter_names`) are not in it. `/spec-change` does not mention it, and
`implement-cases` forbids editing it. Affected: the case runner and anyone adding cases.

## Options

### A. Remove it; `//~` annotations are the only expectations (as in rustc `ui` tests)
The runner walks `tests/data/lang/` (sorted). A file or directory is a case; its id is the path. The
expectations are the `//~ CODE` comments at the end of the line of the primary span, exactly as README
defines them; a case with none must produce no diagnostics. `kind` follows from the layout (`pending/`
is skipped) and `section` is only the header comment, not used by the runner. No `//~^` or other
relative forms are added. Consequences:

Positive:
- One source of truth; adding a case is adding files. No drift, no step that can be forgotten.
- Nothing to bless or regenerate; fits the rule that expected output is never regenerated.

Negative:
- The runner parses annotations itself (it has to anyway, rule 1 in README); a typo in `//~` is not caught
  by a second list: a misspelled code fails the case, but a line with no `//~` at all passes if nothing is
  reported. A silent loss of a case is possible if discovery has a bug.
- No machine-readable list for other tools (CI summaries, a count of cases); they must scan the tree.

### B. Keep it, written by hand
Status quo. Consequences:

Positive:
- A reviewed, explicit list: removing or renaming a case shows in the diff of the index.

Negative:
- Drift is already happening and every spec change must remember to update it.
- `expect` repeats annotations, so a line moved in a case file means two edits.

### C. Keep it, generated by a tool
A command writes the index from the files; a test fails when the file is stale. Consequences:

Positive:
- Same data as A, plus a list for other tools, and a stale list is detected.

Negative:
- Needs a generator, which is a bless-like step (AGENTS: never regenerate expected output).
- The runner can still read the files directly, so the index is redundant for the compiler.

## Decision
Option A because cases.json is the secont source of truth and the implementation of option A is quite small.

## Consequences

A: delete `cases.json`; README layout drops it and says the runner discovers cases and reads expectations
only from `//~` (README is part of the cases, so this is a spec session change); `implement-cases` drops the
sentence about it; RFC §11 states the same. A test checks that the number of discovered cases is not zero.
B: add `cases.json` to the `/spec-change` steps and add the four missing cases.
C: as B, plus the generator and the staleness test in the runner.
